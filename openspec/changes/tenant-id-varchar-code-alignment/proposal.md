# 对齐 tenant_id VARCHAR 代码类型

## 背景

`sql/V011__tenant_id_to_varchar.sql` 已将 Lumax 相关业务表的 `tenant_id` 从 `INTEGER` 改为 `VARCHAR(64)`。数据库字段类型改变后，代码中仍有多处把租户标识当作 `int` / `number` 处理：

- 前端登录会话把 `tenantId` 解析为 `number`，并且只有数字类型才写入 `TENANT-ID` 请求头。
- 后端 Gateway、运行时、计量、敏感词、价格缓存等链路使用 `int()`、`< 1` 或 `number` 类型约束。
- DB 直连查询在 `tenant_id = %s`、`tenant_id IN (%s, 0)` 等语句中仍可能传入整数参数。

本次调整按用户确认的范围执行：业务仍只支持由数字字符组成的租户 ID，但在代码、请求、缓存和数据库访问中统一使用“数字字符串”的表示。租户 ID 可能很长，例如 `2052263773707833345`，不得经过 JavaScript `Number` 或其他会导致精度风险的数值类型转换。

## 问题

如果数据库列已经是 `VARCHAR(64)`，但代码继续传整数租户 ID，可能出现：

1. PostgreSQL 中 `varchar = integer` 类型比较错误。
2. 价格兜底查询中的 `tenant_id IN (%s, 0)` 与 varchar 列类型不一致。
3. 前端或网关对租户标识进行数字类型限制，导致字符串形态的 `tenantId` 无法稳定透传。
4. 敏感词、计量、额度、结算链路对租户 ID 的类型语义不一致。

## 目标

- 将 `tenant_id` / `tenantId` 在代码内统一为数字字符串，例如 `"2052263773707833345"`。
- 保持业务约束：只接受数字字符组成的租户 ID，不支持任意字符串租户。
- 避免精度丢失：前端和后端不得为了处理租户 ID 调用 `Number()`、`int()` 或其他数值转换。
- 默认租户和全局租户使用字符串常量：`"1"` 与 `"0"`。
- 保持 `user_id`、`word_id`、`category_id`、`conversation_id` 等字段的整数语义不变。
- 调整相关测试，覆盖字符串租户 ID 进入前端、后端、DB 参数、Redis key 和敏感词链路。

## 非目标

- 不修改 `sql/V011__tenant_id_to_varchar.sql` 的迁移内容。
- 不支持非数字租户标识，例如 `"tenant-a"`。
- 不重构计量、鉴权、敏感词或前端登录模块的架构。
- 不改变 `total_quota = -1` 表示 unlimited 的既有语义。
- 不改变 lumax-service HTTP API 的字段名，仍使用 `tenantId`。

## 方案概述

新增或复用轻量的租户 ID 校验逻辑：输入按字符串语义处理，输出统一为 `str(value).strip()` 后的数字字符串；空值、非数字、全零值视为无效。该逻辑不得依赖数值转换来判断合法性，以免长数字租户 ID 精度丢失。

后端所有和 Lumax 租户上下文相关的数据结构、运行配置、DB 查询参数、Redis key 拼接和 HTTP payload 都使用规范化字符串。需要进行正数判断的位置改为先规范化，再判断是否为空。

前端登录和会话层将 `tenantId` 类型改为字符串，解析平台返回值时保持数字字符串语义，后续请求只要存在非空 `tenantId` 就写入 `TENANT-ID` 请求头。

测试采用 TDD 方式补齐字符串租户用例，优先覆盖 `2052263773707833345` 这类长数字字符串，再实施最小代码修改。
